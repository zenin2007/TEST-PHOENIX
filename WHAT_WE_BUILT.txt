1. EXECUTIVE SUMMARY & PROBLEM STATEMENT
--------------------------------------------------------------------------------
Traditional end-to-end automated testing frameworks (Playwright, Cypress, Selenium)
depend heavily on rigid element selectors:

    click("#checkout-button")

When product teams rename buttons, move elements into slideout drawers, or refactor
markup, brittle selectors break immediately—even though the core user workflow
operates perfectly.

Conversely, naive "self-healing" AI tools blindly click whatever element seems close
and mask genuine application defects (such as HTTP 500 database transaction failures)
as "healed UI changes", creating disastrous false positives.

TestPhoenix solves this by understanding high-level human intent:

    "Complete checkout with a valid credit card."

It detects interface mutations, analyzes the original intent, inspects live DOM and
accessibility trees, dynamically reconstructs the workflow, and verifies that the
intended outcome actually occurred before certifying the run as SELF-HEALED.

4. CORE ENGINE & BACKEND ARCHITECTURE
================================================================================

A. INTENT-AWARE ENGINE (`testphoenix/`)
--------------------------------------------------------------------------------
1. `models.py`:
   First-class models for `IntentWorkflow`, `IntentStep`, `CandidateElement`,
   `StepStatus` (PASS, SELF_HEALED, FAIL, HUMAN_REVIEW_REQUIRED), and
   `FailureCategory`.
2. `dom_inspector.py`:
   Extracts interactive elements via live JavaScript evaluation. Captures roles,
   accessible names, visible text, placeholders, bounding boxes, aria labels,
   and DOM parent hierarchies.
3. `scoring.py`:
   Deterministic 5-factor scoring engine:
     Score = (0.40 * Semantic) + (0.20 * Role) + (0.15 * Text) +
             (0.15 * Context)  + (0.10 * Structural)
   Domain synonym clusters for both Task management and E-Commerce shopping.
   Stop-word filtering prevents token ratio distortion.
4. `classifier.py`:
   Classifies failures into `ELEMENT_NOT_FOUND`, `AMBIGUOUS_MATCH`,
   `ELEMENT_NOT_INTERACTABLE`, `NETWORK_OR_BACKEND_ERROR`, etc.
5. `engine.py`:
   Executes steps, checks SQLite `healing_memory`, inspects DOM on locator
   failure, evaluates candidates, checks safety gates, replays action, and
   verifies outcome with a 2.5s polling loop for asynchronous React updates.
6. `reporter.py`:
   Structured telemetry and dictionary export with exact scoring percentages.

B. BACKEND API & SQLITE DATABASE (`backend/`)
--------------------------------------------------------------------------------
1. `database.py`:
   SQLite database (`backend/tasks.db`) containing tables:
   - `tasks`: Task management records
   - `orders`: E-commerce orders records
   - `test_runs`: Execution history, durations, and diagnostics JSON
   - `healing_memory`: Persistent cache of verified locator mappings
2. `main.py`:
   FastAPI endpoints:
   - `/api/tasks` (GET, POST with HTTP 500 header simulation)
   - `/api/orders` (GET, POST for shopping cart checkout)
   - `/api/tests/normal`, `/api/tests/self-healing`, `/api/tests/shopping-a`,
     `/api/tests/shopping-b`, `/api/tests/broken-backend`, `/api/tests/ambiguous`
   - `/api/tests/history`, `/api/tests/history/{id}`
   - `/api/healing/memory`, `/api/healing/clear`
   - `/api/evaluation/latest`, `/api/evaluation/csv`, `/api/evaluation/run`
   - `/results`: Serves standalone visual HTML telemetry portal
3. `test_runner.py`:
   Playwright sync test execution. Zero hardcoded Version-B fallbacks.
   Candidates are discovered dynamically from the live browser DOM.
