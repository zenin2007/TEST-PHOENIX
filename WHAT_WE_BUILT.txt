1. EXECUTIVE SUMMARY & PROBLEM STATEMENT
--------------------------------------------------------------------------------
Traditional end-to-end automated testing frameworks (Playwright, Cypress, Selenium)
depend heavily on rigid element selectors:

    click("#checkout-button")

When product teams rename buttons, move elements into slideout drawers, or refactor
markup, brittle selectors break immediately—even though the core user workflow
operates perfectly.

Conversely, naive "self-healing" AI tools blindly click whatever element seems close
and mask genuine application defects (such as HTTP 500 database transaction failures)
as "healed UI changes", creating disastrous false positives.

TestPhoenix solves this by understanding high-level human intent:

    "Complete checkout with a valid credit card."

It detects interface mutations, analyzes the original intent, inspects live DOM and
accessibility trees, dynamically reconstructs the workflow, and verifies that the
intended outcome actually occurred before certifying the run as SELF-HEALED.

2. PRODUCTION FRONTEND ARCHITECTURE (FEATURE-BASED)
================================================================================
The frontend has been transformed from a single-page prototype into a scalable,
production-grade developer platform:

A. APPLICATION SHELL & INFORMATION ARCHITECTURE
--------------------------------------------------------------------------------
- Collapsible Left Navigation Sidebar:
  * Overview        (System health, recently healed, attention items)
  * Tests           (Catalog of multi-domain suites & scenarios with Run buttons)
  * Runs            (Complete execution history with search, filter & pagination)
  * Recovery        (Signature self-healing view & interactive demonstration)
  * Analytics       (8 interactive, backend-driven performance visualizations)
  * Healing Memory  (SQLite persistent locator cache inspection & management)
  * Settings        (Engine parameters, 5-factor weights, database reset)
- One Obvious Primary Action:
  * [▶ Run Test]: Accessible globally from both the top bar and sidebar, opening
    a quick scenario execution modal.
- Progressive Disclosure:
  * Deep technical DOM attributes, failure classifications, and diagnostics JSON
    are kept inside accessible "Inspect Evidence" modals rather than cluttering
    the primary views.

B. REUSABLE UI PRIMITIVES (`frontend/src/components/ui/`)
--------------------------------------------------------------------------------
- `Badge.tsx`: Strict semantic status badges (Pass, Self-Healed, Fail, Review)
- `Button.tsx`: Accessible buttons (Primary, Secondary, Ghost, Danger) with loading states
- `Card.tsx`: Minimalist cards with header, actions, content, and footer
- `Modal.tsx`: Accessible dialog with backdrop blur, focus management, and escape key handling
- `EmptyState.tsx`: High-polish empty state with icon, message, and call-to-action

C. CENTRALIZED API SERVICE (`frontend/src/api/client.ts`)
--------------------------------------------------------------------------------
- Encapsulates all REST communication with the FastAPI backend:
  * Tasks CRUD & controlled failure header injection
  * Orders CRUD & SQLite verification
  * Test history retrieval with limit filtering
  * Playwright scenario execution triggers
  * Healing memory retrieval and cache clearing
  * Evaluation benchmark suite triggers and CSV downloads
  * System health check and database seed reset

3. DEDICATED PLATFORM EXPERIENCES
================================================================================

A. PLATFORM OVERVIEW (`OverviewView.tsx`)
--------------------------------------------------------------------------------
Answers the three critical questions immediately:
1. "How healthy are my tests?"
   - Live health score percentage derived from real passes and verified recoveries.
2. "What was recently healed?"
   - Card highlighting the latest recovery: mutated selector vs. recovered selector,
     intent match score, and direct link to inspect verifier evidence.
3. "What needs attention?"
   - Flags unmasked genuine defects (HTTP 500) and ambiguous target challenges.
- Recent Runs audit table with 1-click inspection.

B. TEST SUITES & SCENARIO CATALOG (`TestsView.tsx`)
--------------------------------------------------------------------------------
Catalog of multi-domain test workflows:
- Version A Task Creator (Baseline Modal)
- Version B Work Item Drawer (Redesigned Self-Healing)
- Store A Audio Storefront (Baseline Modal)
- Store B Sound Experience (Redesigned Drawer Self-Healing)
- Simulated Database Failure (HTTP 500 Defect Preservation)
- Ambiguous Target Challenge (Safety Gate Halting)
- One-click trigger for the full 20-Scenario Benchmark Suite.

C. TEST EXECUTION RUNS (`RunsView.tsx`)
--------------------------------------------------------------------------------
- Real-time search across scenario names, intent strings, and run IDs.
- Status filter tabs: All, Pass, Self-Healed, Fail, Human Review.
- Configurable pagination (10 items per page).
- Columns: Test ID | Intent | Scenario | Recovery | Verification Evidence | Duration | Result | Action.
- Click any row to open the complete "Inspect Evidence" verification modal.

D. SIGNATURE SELF-HEALING VIEW (`SelfHealingDemo.tsx`)
--------------------------------------------------------------------------------
The signature product experience:
- Original Intent: "Complete checkout with a valid credit card."
- Interface Changed: [ Checkout ] (#checkout-btn) ➔ [ Proceed to Payment ] (#proceed-to-payment-btn).
- 8-Step Visual Recovery Timeline:
  01 Test Started ➔ 02 UI Change Detected ➔ 03 Intent Analyzed ➔
  04 Candidates Evaluated ➔ 05 Workflow Reconstructed ➔ 06 Action Replayed ➔
  07 Outcome Verified ➔ 08 SELF-HEALED.
- 5-Factor Candidate Scoring Inspection:
  * Proceed to Payment : 94% (Selected Target)
  * Continue Checkout  : 87%
  * Place Order        : 42%
- Explains why the candidate was chosen (Semantic 40%, Role 20%, Text 15%, Context 15%, Structure 10%).
- Defect Mode (HTTP 500) & Ambiguity Gate (margin < 0.15) interactive toggles.

E. INTERACTIVE ANALYTICS ENGINE (`AnalyticsView.tsx`)
--------------------------------------------------------------------------------
8 backend-driven visualizations:
1. Test Health Trend — Passed vs Self-Healed vs Failed execution batches.
2. Self-Healing Rate — Actual recoveries against recoverable selector mutations (%).
3. Recovery Time Trend — Playwright sync execution duration in milliseconds.
4. Failure Categories — Element Missing, Ambiguous Match, Backend 500, Interactability.
5. Mutation Resilience Matrix — Changed ID, Renamed Button, Modal to Drawer, etc.
6. Recovery Score Distribution — 0.90-1.00, 0.80-0.89, 0.75-0.79, <0.75.
7. Workflows Requiring Recovery — Identifies surfaces undergoing rapid design iteration.
8. Execution Volume — Total test runs recorded in local SQLite database.

F. SQLITE HEALING MEMORY CACHE (`HealingMemoryView.tsx`)
--------------------------------------------------------------------------------
- Displays learned self-healing locator mappings stored in SQLite table `healing_memory`.
- Shows original intent, obsolete selector, recovered selector, confidence, and timestamp.
- Button to clear healing memory cache (`/api/healing/clear`).

G. ENGINE SETTINGS & VERIFICATION GATES (`SettingsView.tsx`)
--------------------------------------------------------------------------------
- Confidence Threshold Gate: >= 0.75
- Ambiguity Margin Gate: >= 0.15
- Mandatory Dual Verification: Active Enforced (UI DOM + SQLite backend check)
- 5-Factor candidate scoring formula weights
- Database reset trigger (`/api/test/reset`)
